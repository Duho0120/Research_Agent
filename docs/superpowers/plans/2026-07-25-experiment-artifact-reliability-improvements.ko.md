# 실험 진행 및 산출물 신뢰성 개선 계획

## 목표

실험 실행, 제출, 판단, 메모리, 다음 계획과 사용자용 산출물이 모두 같은 실행 사실을 사용하도록 정리한다.
이번 계획에서는 피드백 요청 정책 자체를 고도화하지 않는다. 먼저 피드백 판단에 들어가는 점수와 산출물의 신뢰성을 확보한다.

## 핵심 원칙

1. Kaggle 등 제출형 실험의 Best와 다음 base trial은 제출 점수를 우선한다.
2. 로컬 점수는 모델 진단과 보조 판단에 사용하되 제출 점수보다 높은 우선순위를 갖지 않는다.
3. 제출형 실험은 제출 점수 기록이 끝난 뒤 최종 진단과 다음 계획을 생성한다.
4. 사용자 피드백 대기는 실패가 아니라 정상적인 중단 상태로 기록한다.
5. 다음 계획에 사용되는 모델, 피처, 검증, 개선축 메타데이터는 실제 실행 코드와 일치해야 한다.
6. 사용자용 문서는 내부 구조화 데이터에서 생성하되 실제 실행 명령과 파일 경로를 보여준다.

## 1단계: Best 및 base trial 기준 통일

### 문제

- SQLite에는 제출 Best가 별도로 기록되지만 상태 조회의 대표 `best_trial`은 로컬 점수 기준이다.
- 웹 표, CLI 상태, 에이전트 대화, 다음 계획이 서로 다른 Best를 보여줄 수 있다.

### 개선

- 제출형 실험은 `get_best_trial(..., prefer_lb=True)`를 기본으로 사용한다.
- 로컬 연구는 기존처럼 로컬 점수를 사용한다.
- 상태 응답에는 필요하면 `best_trial`과 별도로 `best_local_trial`을 제공하되, UI의 Best 표시는 제출 Best만 사용한다.
- 다음 base trial 선택은 submission log와 SQLite의 제출 Best가 일치하는지 검증한다.
- 기존 Titanic 기록도 동기화 시 동일 기준으로 조회되도록 한다.

### 완료 조건

- Titanic 상태의 대표 Best가 `trial_007`로 표시된다.
- CLI, 웹, 상태 API, 에이전트 질의가 같은 Best를 반환한다.
- 로컬 전용 실험에서는 로컬 Best가 정상적으로 반환된다.

## 2단계: 제출 후 최종 판단으로 실행 순서 변경

### 목표 흐름

```text
계획 확정
→ 코드 작성 및 검증
→ 로컬 실행
→ metrics 수집
→ 제출 파일 사전 검증
→ Kaggle 제출 및 LB 점수 기록
→ 실행 사실 재구성
→ 최종 평가·진단·피드백 판단
→ decision card와 trial memory 기록
→ 사용자용 산출물 생성
→ 다음 trial 계획 생성
```

로컬 전용 실험은 제출 단계를 건너뛰고 실행 사실 재구성부터 이어간다.

### 개선

- `process_workspace_result()`를 제출 이후에 한 번만 호출한다.
- 제출 전에는 metrics와 제출 파일의 형식만 검증한다.
- 제출 후 `metrics`, `submission_run`, 실행 코드에서 최종 evidence bundle을 만든다.
- decision card, memory card, diagnosis, human review가 같은 evidence bundle을 사용하도록 한다.
- 현재처럼 제출 전후로 산출물을 두 번 정리하는 중복 호출을 제거한다.
- 제출 실패 시 다음 계획을 만들지 않고 현재 trial의 제출 재시도 상태로 남긴다.

### 완료 조건

- `workspace_result_cycle.json`에 현재 trial의 LB 점수가 기록된다.
- CV/LB 방향 충돌이 같은 trial의 진단과 피드백 판단에 반영된다.
- 다음 trial 계획은 제출 점수 기록 완료 이후에만 생성된다.
- 산출물 정리는 회차당 한 번만 실행된다.

## 3단계: LangGraph 사용자 대기 상태 정식 분리

### 문제

`blocked_human_review`가 계획 실패로 처리되어 정상적인 사용자 개입 대기가 `failed`로 기록된다.

### 개선

- 그래프에 `awaiting_human_review` 노드를 추가한다.
- 필수 피드백 요청은 LangGraph interrupt/checkpoint 상태로 저장한다.
- 비긴급 요청은 `planned_with_pending_review`로 계속 진행할 수 있다.
- 사용자 답변이 등록되면 같은 thread/checkpoint에서 다음 계획 단계로 재개한다.
- 코드 오류, 제출 실패, 사용자 대기를 서로 다른 상태로 구분한다.

### 완료 조건

- 필수 피드백 발생 시 상태가 `failed`가 아니라 `awaiting_human_review`가 된다.
- 답변 전에는 다음 trial 코드 작성이 시작되지 않는다.
- 답변 후 중복 실행 없이 중단 지점부터 재개된다.

## 4단계: 실행 코드와 메타데이터 일관성 게이트

### 검증 대상

- 모델 및 앙상블 구성
- 주요 하이퍼파라미터
- 피처 목록과 파생 피처
- 전처리
- 검증 방식과 seed
- metric과 objective
- trial ID와 source/base trial
- 제출 컬럼과 제출 파일 경로
- 사용자 인사이트 개선축과 실제 코드 변경

### 개선

- 코드 실행 후 `pipeline_structure.json`과 metrics/runtime metadata를 비교한다.
- 불일치가 있으면 규칙 기반 자동 교정을 먼저 한 번 시도한다.
- 자동 교정할 수 없는 의사결정 핵심 필드는 trial 완료를 차단하고 코드 작성 단계로 한 번 되돌린다.
- 단순 설명 누락은 경고로 남기되 모델·점수·개선축 불일치는 경고만으로 완료시키지 않는다.
- 특정 모델명이 아니라 구조화된 estimator/member/parameter 정보로 검증한다.

### 완료 조건

- 실제 `VotingClassifier` 실행에서 metrics가 `LogisticRegression`으로 남지 않는다.
- 사용자 인사이트 개선안과 실행 코드가 불일치하면 제출 전에 탐지된다.
- 수정 재시도 후에도 불일치하면 원인이 명확한 blocked 상태가 된다.

## 5단계: 사용자용 산출물 정리

### 실험 계획서

- 영문 LLM 원문을 그대로 노출하지 않고 구조화 필드를 한국어 템플릿으로 렌더링한다.
- 기준 trial, 가설, 변경 사항, 유지 사항, 성공 기준, 실패 시 판단을 분리한다.
- “모든 회차 제출” 정책과 충돌하는 제출 생략 문구를 제거한다.

### 파이프라인 구조도

- 실제 실행 코드에서 추출한 전처리, 피처, 분할, 모델과 파라미터를 유지한다.
- 변경된 단계만 명확히 표시한다.
- 코드 위치는 실제 실행에 사용된 파일과 함수만 보여준다.
- sklearn tabular에 한정되지 않도록 estimator, framework, task adapter를 확장 가능하게 둔다.

### 점수 문서

- 로컬 점수, 제출 점수, 제출 상태, Best 여부와 제출 파일의 실제 경로를 보여준다.
- `submit_manifest`가 없어도 execution profile 또는 submission result에서 제출 경로를 찾는다.

### 재현 명령

- `test_step.py`, `train_step.py`, `predict_step.py`를 고정하지 않는다.
- execution profile의 실제 명령과 작업 디렉터리를 사용한다.

### 완료 조건

- trial 산출물 세 문서만 읽어도 무엇을 바꾸고 어떻게 실행했으며 결과가 어땠는지 이해할 수 있다.
- 문서의 모델, 점수, 제출 파일과 내부 JSON 값이 일치한다.
- Titanic이 아닌 워크스페이스에서도 잘못된 고정 명령이나 컬럼명이 나오지 않는다.

## 6단계: 중복 코드와 테스트 탐색 정리

### 개선

- `trial_artifacts.py`의 중복 `_extract_pipeline_facts()` 정의를 하나로 통합한다.
- `trial_user_view.py`의 중복 `render_user_plan()`과 `render_user_scores()` 정의를 제거한다.
- 이전 렌더러가 필요하면 명시적인 legacy 모듈로 분리한다.
- `pytest.ini` 또는 `pyproject.toml`에 `testpaths = tests`와 제외 경로를 설정한다.
- `_archive`, `runs`, `experiments`, `demo_workspaces`의 코드 스냅샷을 테스트 수집에서 제외한다.

### 완료 조건

- `python -B -m pytest -q`만 실행해도 제품 테스트만 수집된다.
- 기존 `409 passed, 1 skipped` 수준의 회귀 테스트가 유지된다.
- 어떤 렌더러와 추출기가 실제로 호출되는지 함수 정의가 하나로 명확해진다.

## 권장 구현 순서

1. Best/base trial 기준 통일
2. 제출 후 최종 판단 순서 변경
3. LangGraph 사용자 대기 상태 분리
4. 메타데이터 일관성 게이트
5. 사용자용 산출물 렌더링 수정
6. 중복 코드와 pytest 탐색 정리
7. 전체 회귀 테스트와 제출 없는 모의 3회 루프
8. 별도 Kaggle 대회에서 실제 3회 제출 검증

## 후속 계획: 피드백 요청 정책 고도화

다음 단계에서 별도로 진행한다. 실험 횟수 자체를 조건으로 사용하지 않는다.

- 긴급 문제는 즉시 요청한다.
- 비긴급 문제는 여러 trial에서 반복되는 불확실성, 개선 정체, CV/LB 불일치, 사용자 답변의 기대 가치와 자율 진행 위험을 누적한다.
- 같은 질문의 반복, 요청 cooldown, 미응답 요청 병합을 관리한다.
- 개선축을 충분히 탐색한 뒤 사용자 판단이 실제로 다음 방향을 바꿀 때만 요청한다.
- 정상적인 실험에서는 10회를 넘어도 요청하지 않을 수 있고, 증거가 누적되면 대략 8~10회 부근에서 자연스럽게 요청될 수 있도록 한다.

이 후속 계획은 1~6단계가 완료되어 피드백 판단 입력값의 신뢰성이 확보된 뒤 구현한다.
